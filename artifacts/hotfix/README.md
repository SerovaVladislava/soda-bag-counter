# Доставка правки без перезаливки образа

Образ весит 648 МБ, и гнать его целиком ради изменения в коде долго. Compose
умеет подменять отдельный файл внутри контейнера свежей версией с диска —
этого достаточно для правок в логике подсчёта.

## Как применить

Всё делается в папке, где лежит `docker-compose.yml` (обычно `soda-bag-counter`).

1. Скачайте в эту папку четыре файла:

   - `docker-compose.override.yml` — отсюда же, из `artifacts/hotfix/`
   - `analytics.py` и `main.py` — из `backend/app/` в корне репозитория
   - `index.html` — из `frontend/`

   Все четыре обязательны: override подменяет каждый из них, и если файла
   нет на диске, Docker создаст вместо него пустую папку, а контейнер не
   запустится. Прямые ссылки:

   ```
   https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/artifacts/hotfix/docker-compose.override.yml
   https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/backend/app/analytics.py
   https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/backend/app/main.py
   https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/frontend/index.html
   ```

   Команды для `cmd` в папке установки:

   ```bash
   curl.exe -LO https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/artifacts/hotfix/docker-compose.override.yml
   ```

   ```bash
   curl.exe -LO https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/backend/app/analytics.py
   ```

   ```bash
   curl.exe -LO https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/backend/app/main.py
   ```

   ```bash
   curl.exe -LO https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/frontend/index.html
   ```

2. Примените:

   ```bash
   docker compose up -d
   ```

   Compose подхватит `docker-compose.override.yml` автоматически — указывать
   его в команде не нужно.

   **Если override уже стоял и вы только обновили `analytics.py`**, этой
   команды недостаточно: конфигурация не изменилась, Compose ответит
   `Running` и не тронет контейнер, а сервер продолжит работать старым
   кодом из памяти. Перезапустите backend явно:

   ```bash
   docker compose restart backend
   ```

3. Проверьте, что правку исполняет **запущенный сервер**, а не просто файл на
   диске. `docker compose exec ... python -c` для этого не годится: он
   поднимает отдельный интерпретатор и всегда покажет файл с диска. Спросите
   сам сервер:

   ```bash
   curl http://localhost:18000/api/rtsp-monitor/status
   ```

   В ответе у активного монитора есть блок `"thresholds"`. Ожидается
   `"zone": [0.21, 0.0, 0.47, 0.28]`, `"solid_min": 0.25` и
   `"min_present_seconds": 10.0`. Если блока `thresholds` нет вообще, в нём
   нет `solid_min` или `zone` начинается с 0.49 или 0.14 — сервер всё ещё на
   старом коде, выполните `docker compose restart backend`.

4. После `docker compose up -d` контейнер пересоздаётся. Начиная с версии
   от 09.10.2026 сервер сам поднимает мониторы, которые работали до
   перезапуска (список хранится в `data/uploads/rtsp_monitor_state.json`;
   явная остановка кнопкой «Остановить» его очищает). Один раз после
   обновления откройте интерфейс, раскройте «Управление RTSP-потоками» и
   нажмите «Анализировать» — дальше перезагрузки ПК и рестарты Docker
   счёт не прерывают. До этой версии после любого перезапуска мониторинг
   стоял, пока кто-то не нажмёт кнопку: на объекте так пропали шесть суток
   (01.10 03:51 — 07.10 09:19).

## Журнал проб: как узнать, что происходило, не сидя у экрана

Живой цикл пишет каждую пробу в `data/uploads/zone_samples.csv`: время,
заполнение зоны, контрольная зона, базовая линия, решение, состояние,
величина движения в кадре (`motion`), сплошность светлого пятна (`solid`:
у мешка над воронкой 0.4–0.8, у солнечных полос и бликов до 0.1 — по ней
система отличает мешок от солнца сквозь крышу). Файл ограничен 25 МБ (старый
переименовывается в `.1`); при обновлении кода с новым набором столбцов
старый журнал тоже уходит в `.1`, а новый начинается с чистого заголовка.
Следить за потоком в реальном времени не нужно — всё, что система видела,
остаётся в журнале.

Сводку по журналу печатает `tools/summarize_samples.py`: когда в зоне что-то
появлялось, сколько держалось, засчитано ли и почему нет. Один раз скачайте
скрипт в `data/uploads` рядом с журналом:

```
https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/tools/summarize_samples.py
```

Дальше в любой момент, хоть раз в смену:

```bash
docker compose exec backend python /app/uploads/summarize_samples.py
```

Пример вывода:

```
Период: 25.09 11:47 - 25.09 13:38 (1.9 ч), проб 3337
Засчитано мешков за период: 1, счётчик на конце журнала: 1

Пустая зона (пробы без мешка):
  медиана 0.164   p95 0.178   максимум 0.180
  действующий порог входа 0.226; запас над p95 пустой зоны: +0.048

Появления в зоне: 3
        начало   длит.  проб    пик  решение
25.09 12:47:25      2с     2  0.356  не засчитан: в зоне 2 с, меньше 10 - перенос мимо камеры
25.09 13:07:29     38с    20  0.364  ЗАСЧИТАН
25.09 13:28:09     28с    15  1.000  не засчитан: заполнение выше 0.85 - объект вплотную к камере
```

На что смотреть:

- «Появления в зоне» пустые, а выгрузки были — порог для этой сцены завышен,
  пришлите журнал для калибровки.
- Строка «НЕ ЗАСЧИТАН - разобрать по журналу» — мешок держался достаточно,
  но счётчик его отверг; тоже пришлите журнал.
- Предупреждение о замершем потоке — камера или источник отдавали одну и ту
  же картинку, за это время счёт невозможен.
- Запас над p95 пустой зоны должен быть положительным: иначе пустая зона
  сама дотягивает до порога и возможны ложные срабатывания.

Если счёт расходится с реальностью, пришлите сам `zone_samples.csv` — по
нему видно, что именно видела система в момент выгрузки.

## Кадры с мешком над бункером - для настройки зоны

Если по сводке видно, что мешки в зону не попадают (появлений нет или они
короткие и слабые), скорее всего камера смотрит не так, как на записях, по
которым зона настраивалась. Нужны кадры текущей сцены с мешком над бункером.
Их отбирает `tools/watch_snapshots.py`: он следит за верхней частью кадра и
сохраняет только те моменты, когда там что-то появилось. Скачайте его в
`data/uploads`:

```
https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/tools/watch_snapshots.py
```

и запустите на рабочую смену (второй аргумент - часы наблюдения):

```bash
docker compose exec backend python /app/uploads/watch_snapshots.py "rtsp://ссылка-потока-из-карточки-Камера-1" 10
```

Кадры появятся в `data/uploads/calib`: `watch-…-a0.31.jpg` - в верхней части
кадра что-то есть, `ref-….jpg` - опорный кадр раз в полчаса. На каждом кадре
нарисованы обе зоны: оранжевая - зона счёта, зелёная - контрольная. Мешок над
бункером должен попадать в оранжевую и не попадать в зелёную. Пришлите те
кадры, где мешок висит над бункером, и один-два опорных. Мониторинг при этом
продолжает работать: скрипт открывает отдельное подключение к камере.

## Обученная модель (детектор мешков)

Если есть обученная на мешках модель YOLO с классом `bag_full` (у заказчика
такая есть — `best.pt`, 40 МБ), положите её в `data/uploads/best.pt`: сервер
берёт модель оттуда, если файл существует, иначе — из образа. Модель
подхватывается при запуске монитора: после копирования нажмите
«Остановить» и «Анализировать» (или `docker compose restart backend` —
мониторинг поднимется сам).

Сейчас единственная рабочая копия этой модели — на ПК заказчика,
`C:\soda-bag-counter\data\uploads\best.pt`. При следующем сеансе AnyDesk
скопируйте её оттуда к себе (передача файлов в AnyDesk) и положите в
`models\best.pt` репозитория: тогда она попадёт в образ и не потеряется.

С такой моделью уверенная рамка полного мешка в зоне над бункером
становится вторым признаком присутствия — наравне с заполнением зоны. В
статусе (`curl http://localhost:18000/api/rtsp-monitor/status`) появится
`"detector_enabled": true`, `detector_seconds` — время одного прогона модели
на этом процессоре (период между прогонами подстраивается сам), а в журнале
проб — столбец `det` с уверенностью детектора. Модель без класса `bag_full`
(в том числе штатная из образа) детектор не включает, и счёт работает
как прежде.

### Что видит модель - кадры и журнал

С версии от 10.10.2026 сервер сам сохраняет кадры, на которых модель видит
мешок: `data/uploads/detector_frames/<дата>/ЧЧ-ММ-СС_класс-уверенность.jpg`.
На кадре - зона над бункером (оранжевая), все рамки модели с классом,
уверенностью и долей рамки в зоне (зелёная - рамка, которая засчитывается),
снизу - заполнение, детектор и счёт. Кадр сохраняется при каждом изменении
картины, но не чаще раза в 15 с; неподвижный мешок на полу - раз в 5 минут;
кадр засчёта - всегда (`..._counted.jpg`). Не больше 300 кадров в сутки,
хранятся 7 дней.

В журнале проб к столбцу `det` добавлены `det_any, det_cls, det_cx, det_cy,
det_ov` - лучшая рамка модели в любом месте кадра: уверенность, класс,
центр и доля в зоне. Сводка `summarize_samples.py` печатает раздел
«Детектор»: когда модель видела мешок, где и почему он не засчитан (вне
зоны, низкая уверенность, класс не `bag_full`).

### Настройка на месте без обновления кода

Зону и пороги можно поменять файлом `data/uploads/zone_config.json`. Он
читается при каждом запуске монитора («Анализировать» или
`docker compose restart backend`). Все ключи необязательны:

```json
{
  "zone": [0.21, 0.0, 0.47, 0.28],
  "control_zone": [0.72, 0.02, 0.97, 0.24],
  "detector_min_conf": 0.6,
  "detector_min_overlap": 0.3,
  "detector_imgsz": 640,
  "detector_labels": ["bag_full"],
  "solid_min": 0.25,
  "baseline_margin": 0.12,
  "min_present_seconds": 10
}
```

Зоны - доли кадра (x1, y1, x2, y2). `detector_labels` - классы модели,
которые открывают эпизод. Если в файле ошибка, действуют настройки по
умолчанию, а причина видна в статусе в поле `config_error`; при успехе в
`config_source` - путь к файлу. Удалить файл - вернуться к умолчаниям.

## Выдуманная история смен в установках до 08.10.2026

До версии от 08.10.2026 сервер при первом запуске сам дописывал в «Историю
мешков по сменам» 30 дней демонстрационных значений для потоков из реестра
и для несуществующего потока «Цех по загрузке реагентов». Эти строки
выглядят как настоящие. Генерация убрана, а накопившиеся строки чистит
`tools/reset_shift_history.py`: он удаляет потоки, которых нет в реестре,
и всё старше указанной даты (первой, которую нужно оставить). Скачайте его
в `data/uploads` и выполните, подставив дату начала настоящего подсчёта:

```bash
curl.exe -L -o data\uploads\reset_shift_history.py https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/tools/reset_shift_history.py
```

```bash
docker compose exec backend python /app/uploads/reset_shift_history.py 2026-09-27
```

```bash
docker compose restart backend
```

Исходный файл истории сохраняется рядом как `bag_shift_history.json.bak`.

## Запись суток с камеры - для настройки по реальному видео

Самый надёжный способ довести счёт: записать сутки работы и проверить
подсчёт на этой записи до отправки правки, а не по журналу после. Скрипт
`tools/record_day.py` пишет поток кусками по 10 минут в уменьшенном размере
(1024x768, 2 кадра/с, 10-20 МБ на кусок, 1-3 ГБ за сутки); ffmpeg в
контейнере уже есть. Скачайте скрипт в `data/uploads`:

```
https://raw.githubusercontent.com/SerovaVladislava/soda-bag-counter/main/tools/record_day.py
```

и запустите (второй аргумент - часы записи):

```bash
docker compose exec -d backend python /app/uploads/record_day.py "rtsp://ссылка-потока-из-карточки-Камера-1" 24
```

Куски появляются в `data/uploads/recordings`, имя файла - местное время начала
куска. Ход записи виден в `data/uploads/recordings/record.log`. Мониторинг
при этом работает, это отдельное подключение к камере. Остановить раньше:

```bash
docker compose exec backend pkill -f record_day.py
```

Пришлите куски за время, когда были выгрузки, кусок солнечного дня
(14:00-15:40) и `zone_samples.csv` за тот же день.

## Как откатиться

Удалите `docker-compose.override.yml` и `analytics.py`, затем `docker compose up -d`.
Контейнер вернётся к коду из образа.

## Когда так делать не стоит

Подмена файла — временная мера между релизами. Если правок накопилось много
или менялись зависимости, лучше собрать новый образ: подменённый файл должен
оставаться совместимым с остальным кодом внутри образа.
